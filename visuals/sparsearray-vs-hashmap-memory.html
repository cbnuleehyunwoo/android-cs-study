SparseArray는 왜 HashMap보다 가벼울까

정수 키 1,000개를 넣었을 때 컨테이너가 차지하는 메모리를 셌습니다. 값 객체는 양쪽이 똑같이 가리키므로 빼고, 키는 리소스 ID처럼 큰 정수라고 가정했습니다. 차이는 항목마다 따로 생기는 Node와 박싱된 Integer 객체에서 나옵니다.

가벼운 대신 무엇을 포기하나

SparseArray는 키를 정렬된 int[]에 담고 이진 탐색으로 찾습니다. 메모리 절약과 아래 비용이 같은 설계에서 나옵니다.

조회

HashMap평균 O(1)SparseArrayO(log n)

HashMap은 해시로 버킷을 바로 찾습니다. SparseArray는 이진 탐색이라 1,000개면 최대 10번쯤 비교합니다.

삽입

HashMap평균 O(1)SparseArrayO(n)

키가 중간에 들어가면 뒤쪽 원소를 System.arraycopy로 한 칸씩 밉니다. 오름차순으로 넣으면 끝에 붙여서 빠릅니다.

삭제

HashMapNode 해제SparseArray지연 압축

값 자리에 DELETED 표시만 남깁니다. 다음 size()·keyAt() 때 gc()로 한 번에 당기고, 배열 크기는 줄지 않습니다.

빈 상태

HashMap40 BSparseArray24 B

Android 14부터 SparseArray()는 모든 인스턴스가 공유하는 빈 배열로 시작해 객체 하나뿐입니다. 13 이하는 생성 즉시 11칸 배열 두 개를 만들어 136 B로, 빈 HashMap보다 컸습니다.

실전 질문

HashMap 대신 SparseArray가 더 효율적인 시나리오와 트레이드오프는?

키가 int이고, 항목이 수백~수천 개 이하이며, 조회 속도보다 메모리가 중요한 곳에서 유리합니다. 공식 문서도 수백 개 정도까지는 성능 차이가 50% 미만으로 크지 않다고 설명합니다.

  • 잘 맞는 곳: View ID → 객체 캐시, 어댑터 position → 상태, 오래 살아 있는 작은 매핑. 값도 원시 타입이면 SparseIntArray·SparseBooleanArray·SparseLongArray로 값 박싱까지 없앱니다. 키가 long이면 LongSparseArray를 씁니다.
  • 성능: 조회는 O(log n), 정렬 순서 중간에 넣는 삽입은 O(n)입니다. 수만 개 이상이거나 삽입·삭제가 잦으면 HashMap이 낫습니다.
  • 사용성: Map 인터페이스가 아니라서 컬렉션 API와 map·filter 같은 확장을 바로 쓸 수 없습니다. android.util 클래스라 로컬 JVM 단위 테스트에서는 Robolectric이 필요하고, 순수 JVM에서 쓰려면 androidx.collection.SparseArrayCompat를 씁니다.
  • 순회 순서: 키 오름차순이 보장됩니다. HashMap은 순서를 보장하지 않습니다.
계산 기준
  • ART 기준: 객체 헤더 8바이트(클래스 참조 4 + lock word 4), 힙 참조 4바이트(64비트 기기도 동일), 배열 헤더 12바이트(헤더 8 + length 4), 객체 크기는 8바이트 단위로 올림.
  • HashMap: 객체 40B, Node 24B(hash·key·value·next), Integer 16B. 테이블은 첫 put에 16칸, 항목 수가 용량×0.75를 넘으면 두 배. 해시 충돌·트리화는 없다고 가정했습니다.
  • SparseArray: 객체 24B. Android 14 이상 기준으로 키 int[]와 값 Object[]는 빈 배열에서 시작해 꽉 차면 약 두 배(growSize). newUnpaddedArray가 정렬 패딩 자리까지 칸으로 써서 8칸 요청이 9칸이 됩니다. 12KB 이상인 int[]는 페이지 단위(여기서는 4KB)로 잡혀 키 배열이 값 배열보다 길어질 수 있습니다. 16KB 페이지 기기는 큰 N에서 SparseArray가 더 커집니다.
  • -128~127 범위 정수는 Integer 캐시를 공유하므로 새 객체를 세지 않았습니다. Int 값 모드에서 값은 캐시 밖의 큰 정수로 가정했습니다.
  • 값 객체(String)는 두 컨테이너가 똑같이 가리키므로 제외했습니다. 실제 수치는 이 레포 앱의 카드 ②에서 컨테이너를 붙잡아 두고 힙 덤프의 retained size로 확인할 수 있습니다. 채우는 동안의 할당량은 앱이 직접 세어 이 계산식과 비교합니다.
