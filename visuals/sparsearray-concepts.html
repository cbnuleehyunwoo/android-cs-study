SparseArray 동작 원리

HashMap은 해시로 자리를 계산하고, SparseArray는 정렬된 키 배열에서 이진 탐색으로 찾습니다. 메모리 차이, 속도 차이, 삭제 방식까지 전부 이 한 가지 설계 차이에서 나옵니다. 아래에서 이름의 뜻, 오토박싱, 실제 동작을 차례로 보고 직접 넣고 빼 봅니다.

HashMap<Int, V>
key→Integer 박싱→hashCode()→& (n−1)→버킷→Node 체인

항목마다 Node 객체를 만들어 버킷 배열에 매답니다. 평균 O(1)로 바로 찾아갑니다.

SparseArray<V>
key (int 그대로)→mKeys[]에서 이진 탐색→같은 인덱스의 mValues[i]

배열 두 개가 전부입니다. 항목마다 생기는 객체가 없고, 대신 찾을 때 O(log n)이 듭니다.

개념 2 · 오토박싱

int는 값이고, Integer는 객체입니다

      개념 4 · 소스 읽기

      AOSP 코드에서 핵심만

      android.util.SparseArray의 실제 로직을 줄인 것입니다. 위에서 본 동작이 그대로 코드에 있습니다.

      get · 이진 탐색 한 번

      public E get(int key, E valueIfKeyNotFound) {
    int i = ContainerHelpers.binarySearch(mKeys, mSize, key);
    if (i < 0 || mValues[i] == DELETED) {
        return valueIfKeyNotFound;
    }
    return (E) mValues[i];
}

      못 찾으면 ~lo(비트 반전)를 돌려줍니다. 항상 음수라서 "없음"을 표시하면서 동시에 들어갈 자리도 알려 줍니다. ~(-3) = 2처럼 다시 뒤집으면 삽입 위치가 나옵니다.

      remove · 표시만 하고 미루기

      public void delete(int key) {
    int i = ContainerHelpers.binarySearch(mKeys, mSize, key);
    if (i >= 0 && mValues[i] != DELETED) {
        mValues[i] = DELETED;
        mGarbage = true;
    }
}

      삭제할 때마다 배열을 당기면 매번 O(n)입니다. 그래서 자리를 비워 두기만 하고, 인덱스가 필요한 size(), keyAt(), valueAt() 같은 호출이 올 때 gc()로 한 번에 압축합니다.

      put · 찾고, 재사용하고, 밀어 넣기

      public void put(int key, E value) {
    int i = ContainerHelpers.binarySearch(mKeys, mSize, key);
    if (i >= 0) { mValues[i] = value; return; }   // 있으면 교체
    i = ~i;                                         // 삽입 위치
    if (i < mSize && mValues[i] == DELETED) {      // 빈 자리 재사용
        mKeys[i] = key; mValues[i] = value; return;
    }
    if (mGarbage && mSize >= mKeys.length) {       // 꽉 찼으면 먼저 압축
        gc();
        i = ~ContainerHelpers.binarySearch(mKeys, mSize, key);
    }
    mKeys = GrowingArrayUtils.insert(mKeys, mSize, i, key);
    mValues = GrowingArrayUtils.insert(mValues, mSize, i, value);
    mSize++;
}

      GrowingArrayUtils.insert는 System.arraycopy로 i 뒤를 한 칸씩 밀고, 자리가 없으면 크기를 두 배로 늘린 새 배열에 복사합니다. 키 순서를 유지해야 이진 탐색이 성립하기 때문입니다.

      gc · DELETED를 건너뛰며 앞으로 당기기

      private void gc() {
    int[] keys = mKeys;
    Object[] values = mValues;
    int o = 0;
    for (int i = 0; i < mSize; i++) {
        if (values[i] != DELETED) {
            if (i != o) {
                keys[o] = keys[i];
                values[o] = values[i];
                values[i] = null;
            }
            o++;
        }
    }
    mGarbage = false;
    mSize = o;
}

      배열을 새로 만들지 않고 제자리에서 당깁니다. 그래서 배열 크기(용량)는 줄어들지 않습니다. 이 gc()는 GC(가비지 컬렉터)와는 무관한 SparseArray 내부 메서드입니다.

      개념 5 · 한눈에 비교

      연산별 차이

      항목HashMap<Int, V>SparseArray<V>
      조회평균 O(1). 충돌하면 체인을 따라감. 한 버킷에 8개가 쌓이고 테이블이 64칸 이상이면 트리로 바뀜O(log n) 이진 탐색
      새 키 삽입평균 O(1). 용량×0.75 초과 시 테이블 두 배 + 전체 재배치O(n). 중간 삽입은 뒤쪽을 밀어야 함. 오름차순 삽입은 끝에 붙어서 빠름
      삭제Node를 체인에서 떼어냄. Node와 Integer는 GC 대상DELETED 표시 후 나중에 gc()로 압축. 용량은 유지
      항목당 객체Node 1개 + Integer 1개 (캐시 범위 밖일 때)없음
      순회 순서보장 안 됨키 오름차순. keyAt(i), valueAt(i)로 반복자 할당 없이 순회
      null 키1개 허용불가 (키가 int)
      값으로 찾기containsValue는 equals 비교indexOfValue는 == 참조 비교. 내용이 같은 다른 객체는 못 찾음
      인터페이스Map 구현. 컬렉션 API와 호환Map 아님. androidx.core의 forEach, keyIterator 같은 확장 일부만 있음
      단위 테스트순수 JVM에서 동작android.util라서 로컬 테스트는 Robolectric 필요

      무엇을 쓸지 정하는 질문

      위에서부터 차례로 답해 보세요.

      1. 키가 int나 long인가요?아니면 HashMap. 항목이 수백 개 이하로 작으면 메모리를 아끼는 ArrayMap도 후보입니다.
      2. 다른 API에 Map으로 넘겨야 하나요?그렇다면 HashMap. SparseArray는 Map을 구현하지 않습니다.
      3. 항목이 수천 개를 넘거나 중간 삽입·삭제가 아주 잦나요?그렇다면 HashMap이나 IntObjectMap. 공식 문서는 수백 개 정도까지는 성능 차이가 50% 미만이라고 설명합니다.
      4. 값도 원시 타입인가요?int면 SparseIntArray, boolean이면 SparseBooleanArray, long이면 SparseLongArray. 키가 long이면 LongSparseArray.
      5. 순수 JVM 단위 테스트에서도 쓰나요?그렇다면 SparseArrayCompat. 아니면 SparseArray로 충분합니다.

      메모리 숫자 비교는 SparseArray vs HashMap 메모리 페이지에 있습니다.
